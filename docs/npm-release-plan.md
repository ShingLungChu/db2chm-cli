## 1. 最终交付目标

用户安装对应平台的 npm 包后，使用统一的 db2chm 命令，连接受支持的数据库，以只读方式查询元数据，按表名过滤并生成可在 Windows HTML Help 中使用的 CHM。Agent 通过独立 skill 调用相同的 CLI。

已经确定的约束：

- 继续使用 Java。用户预装 Java；npm 包不捆绑 JRE/JDK。
- 首期四个目标：Windows x64、macOS Intel x64、macOS Apple Silicon arm64、Linux x64。Linux arm64 进入后续版本。
- Windows 编译后端首选 HHC；macOS/Linux 首选 chmcmd。Windows x64 指宿主平台，允许经过验证的 32 位 HHC 在其上运行，不能把它误标为原生 x64 二进制。
- 单个平台实际安装所需的压缩包下载总量严格小于 15,000,000 字节。统一入口、平台包及默认传递依赖全部计入；不能用拆包或安装时补下载规避上限。
- 默认安装链路不依赖 Maven、FPC、WSL、Docker、系统提权或本机编译。受许可限制的外置 JDBC 驱动作为明确记录的额外前提。
- 保留 Oracle、MySQL、达梦、Vastbase、KingbaseES 五种数据库的适配范围。实际支持的数据库版本和 OS 最低版本须有对应证据。
- CLI 支持非交互运行、稳定退出码、JSON 输出、表名模糊匹配和安全的凭据输入。
- 产品仅访问元数据。固定并审计查询与只读会话配置，不提供用户 SQL、DDL、写 DML、DCL、提权或任意存储过程执行入口。DELETE 属于 DML，同样属于禁止范围。

计划采用 Node.js 22/24 和 Java 8/17/21 作为运行验证基线；最低版本在 T00 中结合驱动与工具链冻结。Java 8 字节码兼容性与驱动实际支持的 Java 版本分别验收。

目标调用链：

    skill 操作说明
        → db2chm CLI / Node 启动器
        → Java 元数据查询与过滤
        → HTML、HHP、HHC、HHK 生成
        → HHC 或 chmcmd 进程
        → CHM 与结构化结果

skill 是操作说明，真实访问和安全限制由 CLI/Java/数据库权限共同实现。

驱动采用“有依据才分发”的规则：允许再分发且体积合适的受支持驱动可内置或拆成可选数据库包；受限驱动通过显式本地路径加载，并固定数据库类型与已认可的驱动类。默认不自动下载全部驱动。T03 必须给出五种数据库逐项结论，不能把“提供适配器”等同于“npm 安装后驱动已就绪”。

15 MB 计量同时报告两条路径：直接安装平台包；安装统一入口后自动选择平台包。若某数据库使用额外驱动包，其宣称的完整安装路径也计入对应驱动下载量。外置驱动的额外大小与前提单独列明。控制目标为 12 MB 内，15 MB 为硬门槛；不捆绑数据库服务端或 Java 运行时。

## 5. CLI、过滤与安全交付约定

计划提供以下命令，具体选项在 T04 固定后同步到帮助、JSON schema、skill 和文档：

    db2chm --help
    db2chm --version
    db2chm doctor --json
    db2chm tables list --config ./connection.json --include "biz_*" --exclude "*_bak" --json
    db2chm export --config ./connection.json --include "*order*" --out ./out/dict --json

连接配置中的密码由环境变量 DB2CHM_PASSWORD 或显式 stdin 输入提供。stdin 不能同时承担配置和密码输入；命令解析时拒绝冲突。默认运行不交互、不写出密码；旧 --password 的兼容策略须明确，不再作为推荐方式。

### 5.1 输出与错误

- JSON 模式 stdout 只输出一个合法 JSON 结果；进度、编译器输出和诊断进入 stderr。结果含 schemaVersion、ok、command、数据/输出路径、使用的编译器、表数量，以及稳定的 error.code；不含秘密。
- help/version 可在未安装 Java 的情况下由启动器给出。doctor 能准确列出 Java、平台包、编译器及所选驱动的状态。
- 参数缺值、重复冲突、不受支持数据库/平台均明确报错；禁止静默吞掉无效数值。
- 建议退出码：0 成功；2 参数错误；3 环境/依赖缺失；4 连接/认证失败；5 元数据/无表可导出；6 渲染/编译失败；7 文件错误；8 安全策略拒绝；124 超时；130 取消。最终以契约文档为准。
- 默认不覆盖已有有效成果；在独立临时目录完成本次流水线后再发布输出。失败、进程中断、文件被占用、旧 CHM 残留均不得成为成功证据。

### 5.2 表过滤

- 首期采用 glob，支持 * 和 ?；例如 "*order*" 表示模糊包含。暂不开放任意正则表达式或 SQL LIKE 片段。
- 多个 include 取并集，exclude 在其后扣除；schema 限制与过滤共同生效，exclude 优先。未提供 include 表示当前授权 schema 内全部基础表。
- 默认按实际表名区分大小写，提供明确的忽略大小写选项；不同数据库的结果不能由本机 locale 改变。
- 过滤发生在读取逐表字段和生成页面之前。tables list 与 export 使用完全相同的表集合与排序。
- list 无匹配时成功返回空数组；export 无匹配时返回 NO_TABLES_MATCHED 和非零退出码，不生成假成功 CHM。
- 保留 --tables 的旧 mock 数量语义或迁移为 --mock-tables；不能复用它表示表名，以免老脚本发生静默行为变化。

### 5.3 安全边界

- 不依赖 DELETE/DROP 等字符串黑名单判断安全。所有运行 SQL 来自受审计的固定元数据查询和只读会话配置；值使用 PreparedStatement，不能绑定的标识符来自授权元数据并按对应数据库规则处理。
- schema、表过滤、标题、路径、URL 属性均不能转成附加 SQL、HHP 选项或 shell 指令。拒绝标题中的换行等工程文件注入；HTML/HHC/HHK 转义必须覆盖数据库注释与特殊表名。
- JDBC 按数据库类型解析并采用属性许可列表，拒绝多语句、初始化 SQL、角色切换、任意插件类/SocketFactory 等超出产品需要的能力；不能仅检查 URL 前缀。
- 固定数据库类型与认可的驱动类映射。外置驱动是调用者显式提供的可信可执行依赖，校验来源/受支持版本；不把任意恶意 JDBC JAR 纳入安全保证。
- 使用最小权限数据库账号，并在适用数据库/驱动上启用只读会话、连接/查询超时。setReadOnly 不是权限隔离的替代品；不支持时必须有数据库权限与产品策略的可审计结论。
- 日志、JSON、异常栈、连接配置、生成 HTML 和调试包都检查脱敏。当前完整 JDBC URL 打印与 ConfigStore 序列化密码的路径需要审计和修正。
- 编译器使用独立 argv 调用；不拼接 shell 字符串，不接受任意额外编译器指令。取消/超时应终止本次子进程并保留明确错误。
- 用非生产只读账户验证注入输入无法改变对象、数据、角色和权限。需要建测试表的准备步骤由独立测试夹具/管理员账号完成，产品账号不执行这些写操作。

### 6.1 验证矩阵

- 平台：Windows x64、macOS x64、macOS arm64、Linux x64，均从最终 tgz/registry 安装；不从源码目录偷用工具、驱动或环境变量。
- 运行环境：冻结后的 Node/Java 最低版本及主要支持版本；检查 JAVA_HOME、PATH、Java 缺失、驱动缺失、不支持平台、空格/中文安装路径、无写权限目录。
- 数据库：五种数据库每种至少一个冻结版本，按正式声明支持的平台组合记录真实连接、列表、字段读取、过滤与小规模 CHM 导出。尚无环境的组合标为未验证，不能用 mock 补成“已支持”。
- 文档内容：中文标题、中文表名和注释、HTML 特殊字符、空注释、主键、字段类型/默认值/可空性、跨页链接；增加 1,000 表×20 列规模样例以检查资源消耗和目录/索引规模问题。
- 编译功能：覆盖项目实际生成的编码、Binary TOC、HHK 与全文搜索；解包校验和 Windows Viewer 交互验收分别记录。解包成功不能代替搜索/目录可用。
- 异常：恶意/特殊输入、URL 不允许的属性、认证/权限不足、连接/查询/编译超时、取消、旧成果、锁定输出、编译器崩溃、平台可选依赖缺失。
- 只读性：产品账号会话实际 SQL、对象/数据/权限前后摘要均无非预期变动；测试环境准备产生的写操作单独记录。

最低 OS 与 libc 版本以实际二进制依赖和最老受测环境确定。当前 macOS/Linux 最新 hosted runner 通过，不代表已经覆盖所有旧系统。Alpine/musl 与 Linux arm64 不纳入首期稳定承诺。

## 7. 可复现与发布约定

- 构建固定 Maven 依赖、FPC 源码/工具链、npm lockfile、基础镜像与 Actions 提交；保存最终 native 动态依赖和版本。
- 发布使用已验收的同一份 JAR、native 文件与 tgz，不在 publish 阶段重新构建。
- 同一固定输入在干净环境重复构建，比较 payload 文件哈希；为 JAR/归档设置确定性时间戳。CHM 或归档仍存在不可消除的时间元数据时，明确记录差异和逻辑内容对比，不能宣称已实现字节级复现。
- 包仅按 files 许可列表收录运行必要文件。自动排除 JRE、FPC、测试库、真实导出、密钥、连接配置、缓存和临时产物。
- 许可证、第三方声明、源码获取方式、受分发约束的文件清单及 SBOM 随交付齐备。存在未解决分发问题的组件不能进入正式 tarball。
- 发布身份与 npm scope 权限在 G0 作为外部依赖明确；CI 发布优先采用所选 npm/runner 支持的受控身份方式，不在源码中保存令牌。
- 先发布四个平台的相同版本到 beta/next，再发布统一入口并验证 registry 安装。全部完成后才将该版本切到 latest。
- npm 多包发布不按单笔事务处理：部分失败时保留旧 latest，重试缺失包；回滚主要恢复 dist-tag 到上一已验收版本，不以删除已发布版本作为常规办法。

## 9. 第一批执行任务

1. T00：比较两份源码，冻结 Git 基线、版本矩阵与命令/退出码草案，建立任务状态和证据目录。
2. T01：在干净 Windows runner/VM 复现项目 tools/hhc 的启动问题，对照同源完整 Workshop 文件集，确认实际所需 DLL、版本、路径和分发结论。
3. T02：将已通过的包管理器可行性工作流升级为固定源码构建，先交付三份 chmcmd 二进制及依赖/尺寸报告。
4. T03：完成五种 JDBC 驱动的分发和加载清单；用真实 tarball 样机提前验证 15 MB 预算。
5. T04：冻结 doctor/list/export、凭据、JSON、退出码和过滤语义，之后进入安全核心与编译器后端的实施。

本批交付物可以是验证脚本、构建产物、报告和命令契约；不能仅以文字“可行”替代可重复执行的证据。发现 HHC 或驱动方案不可分发/超体积时，应在此阶段确定备选，不拖到 T12。
