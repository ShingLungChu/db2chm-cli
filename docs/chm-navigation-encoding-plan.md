# CHM 中文导航乱码：原因分析与校验、修复计划

日期：2026-10-26；实施更新：2026-10-27。阶段：编码补丁与自动校验已实现，完整验收进行中。G4 与发布候选按实际证据放行。

## 1. 现象与影响范围

用户截图红框位于 Windows HTML Help 的“目录”树，属于 TOC；“索引”标签页对应 HHK 关键字索引，需要分别验收。

固定中文节点“封面、表目录、表结构”乱码，英文表名可以显示。三个固定节点与数据库字段无关，现有产物的源文件也保存着正确中文。

对本机 Oracle、达梦、Vastbase 的三表样例和筛选样例共六份既有 CHM 做只读检查，六份均发现相同的导航编码不一致。原 CHM 哈希在检查前后保持不变。真实表名、原始导航流和数据库配置保留在本机，不随本计划公开。

## 2. 已确认的原因

### 2.1 Java 输出策略将正文编码用于全部工程文件

- `NativeCompiler.java:18` 为 chmcmd 选择 UTF-8，为 HHC 选择 GBK。
- `CliRunner.java:123` 将该字符集传入 HTML 渲染器。
- `CliRunner.java:126` 又把相同字符集传入 ChmBuilder，用于 HHP、HHC、HHK。
- `ChmBuilder.java:81` 启用 Binary TOC，`:89` 固定 `Language=0x804`，对应简体中文。

因此当前 chmcmd 路径的正文、工程文件和导航输入全部是 UTF-8，而 CHM 声明的目标语言仍是简体中文。

### 2.2 编译后的导航流没有完成目标代码页转换

对现有 CHM 内部流的检查结果：

| 项目 | 实际值 | 结论 |
| --- | --- | --- |
| `#SYSTEM` 的语言标识 | `0x804` | 简体中文 |
| `#TOCIDX` | 存在 | 已生成二进制目录；是否被阅读器使用需另行确认 |
| `#STRINGS` 的三个固定中文节点 | 存在对应 UTF-8 字节，不存在对应 GBK 字节 | 与当前中文导航解码路径不一致 |
| `#SYSTEM` 窗口标题 | 原始 UTF-8 字节 | 同样存在标题乱码风险，实际窗口显示需复核 |

“封面”的 UTF-8 字节是 `E5 B0 81 E9 9D A2`，按 GBK 解释得到“灏侀潰”，与截图相符。“表目录”“表结构”也可通过相同误解码得到截图中的乱码形态。

这确认了本次根因：**UTF-8 的导航字符串进入 CHM 内部元数据后，在 Windows 导航链路中被按中文 ANSI/CP936 解释。** 源 HTML 中的 UTF-8 meta 标签不能控制二进制 TOC 字符串的解码。

固定 FPC 源码 `de69d52048cf52c72ebfeef61617c04c9bc2005c` 的 `chmsitemap.pas` 直接从文件读字节到 String；`chmwriter.pas` 的 AddString 又直接按字节写入 `#STRINGS`。本次编译链没有在这些边界落实目标代码页转换。不能据此笼统断言 chmcmd 不支持中文；需要修正我们使用的输入、内部文本及输出元数据契约。

### 2.3 关键字索引还存在另一项一致性风险

六份产物的 `$WWKeywordLinks/BTree` 头均为 codepage=1252、LCID=0；固定源码对应位置也写死了这两个值。它们与 HHP 的 `0x804` 不一致。

当前真实样例的索引项为英文，本次截图也没有展示 HHK 标签页。中文关键字显示、排序、检索是否正确，尚不能直接从目录乱码推定，必须增加专门样例。索引键使用 UTF-16 的环节还需检查隐式 String→UnicodeString 转换是否依赖构建主机默认代码页。

## 3. 之前为什么没有发现

已有自动校验主要覆盖生成退出状态、新 CHM 签名、HTML/CSS 解包后的 SHA-256、链接与页面编码。它们可以在导航字符串已经编码错误时继续通过。

二进制目录、窗口标题、关键字 BTree 和全文搜索属于另外的验收对象。即使 HHC/HHK 源文件解包后没有改变，也不能证明编译后的导航和索引正确。Windows Viewer 交互此前保持 pending；当前目录显示已获得失败证据，应改为 failed。

## 4. 顺序与交付标准

| 阶段 | 工作 | 交付与通过标准 |
| --- | --- | --- |
| A：失败基线 | 冻结现有产物哈希、截图和内部流取证；建立不依赖数据库的最小样例 | 当前产物在导航编码检查中稳定失败；样例含三个固定中文节点、中文/英文表名、中文标题和关键字 |
| B：编码边界验证 | 分别验证正文编码、工程输入编码与导航元数据编码；用少量离线样例比较“GBK 工程输入＋UTF-8 正文”和“UTF-8 输入＋显式元数据转码” | 每个候选均检查编译后的目录、标题、HHK；不能仅以界面上三个节点恢复正常选定方案 |
| C：落实修复 | 引入显式编码配置；按目标语言处理元数据，修正 chmcmd 必要的转码和索引头 | Windows、macOS、Linux 构建得到相同逻辑文字；不依赖构建主机 ANSI 设置；不能编码时明确失败，不静默写入问号 |
| D：自动回归 | 增加内部流/索引语义校验，同时保留正文解包检查 | 未修复产物失败，修复产物通过；目录节点、标题、关键字及目标页逐项匹配期望；大规模样例覆盖全部条目 |
| E：Windows 阅读验收 | 分别操作目录、索引、搜索和页面跳转，保存截图与结果 | 四个平台编译出的 CHM 均在 Windows 上正常显示、检索和跳转；交互证据齐备 |
| F：npm 与真实样例回归 | 重建原生后端和平台包，安装后复验，再检查三库缓存样例及必要的真实导出 | 同一份已验收 tgz 可追溯；源码/补丁/哈希/依赖报告更新；安装下载链仍严格小于 15,000,000 字节 |

### C 阶段的建议实现

1. 将单一 `compiler.charset` 所承担的职责分开：HTML 正文编码、工程输入编码、CHM 导航目标代码页、目标 LCID。当前简体中文配置明确绑定 `0x804` 与 CP936；chmcmd 的正文可继续使用 UTF-8。
2. 优先保持 UTF-8 工程输入，在 chmcmd 中明确解码成 Unicode，再按 CHM 对应字段要求序列化：`#STRINGS`、`#SYSTEM` 标题等按目标代码页，关键字的 Unicode 字段按格式写入 UTF-16LE。写入偏移和长度按最终字节计算。
3. 同步检查 BTree 的 LCID、代码页、排序及键值转换。源输入的字节编码、二进制字段的格式与排序规则要分别处理。
4. B 阶段可验证较小的 Java 工程文件编码调整。只有四平台目录、标题、中文 HHK 和搜索全部通过，才能采用该较小方案；主机默认编码造成的隐式转换必须消除。
5. HHC 使用独立的编码配置做回归。当前宿主 HHC6003 不视为完整编译成功；Windows 的 HHC 优先、缺席时 chmcmd 兜底规则继续按现有约定执行。
6. chmcmd 修改保存为可审计源码补丁，纳入四平台固定源码构建；更新源码归档、原生哈希、动态依赖和运行组件清单。

本计划不将“修改 HTML meta 标签”或“关闭 Binary TOC 后暂时显示正常”作为最终完成标准。Binary TOC 和 1,000×20 场景都要覆盖。

## 6. 最终验收条件

- 固定三个中文节点、中文窗口标题和中文表名均与期望字符串逐字一致。
- 中文关键字索引能显示、检索并跳转到正确表页；目录点击与页内链接均正确。
- 全文搜索覆盖已知中文词与 ASCII 表名，结果能打开正确页面；单独记录搜索实现限制。
- 本轮已发现的六份产物按修复方案重新生成并通过相同检查；保留原失败样本用于回归。
- 四个平台产物的导航语义一致，编码行为不随构建主机 locale 漂移。
- 无静默丢字、问号替换或乱码；不可表示输入给出可操作错误并拒绝发布成果。
- 原正文、数据库安全、超时、事务输出和包体积检查继续通过。

当前处理：T07 重新打开，T09/G4 标为中文导航缺陷阻断。现有元数据读取、筛选和正文解包证据保留其原有有效范围，不能替代完整 CHM 阅读验收。

## 7. 实施中新增的证据与方案

1. 已复现并建立最小公开中文夹具，覆盖标题、三个固定目录节点、中文与混合表名、转义字符、长名称及中文/ASCII 全文查询。
2. 仅修正 `#STRINGS`、`#SYSTEM` 后，Windows 阅读器仍可通过文本 HHC/HHK 显示乱码。补丁因此也将归档内的 HHC/HHK 转为 CP936，声明与实际字节一致；外部工程文件与正文保持 UTF-8。
3. 中文 HHK 键明确从 UTF-8 解码成 Unicode，再写 UTF-16LE；关键字与搜索头的代码页为 936、LCID 为 0x804。修正字符串块边界和关键字叶块链，避免大规模样例跨块后产生错误偏移或自环。
4. 全文搜索还涉及 `$OBJINST`。上游写死了 1252/1033、附加搜索对象，以及西文字符大小写/重音映射。仅修正搜索头或更改词项编码不能使中文查询通过。中文配置需要一致的搜索对象元数据、CP936 双字节处理和按中文字符记录的词项位置；不能套用西文字符转换表。
5. 已在 Windows 自带中文 CHM 中只读核对代码页、词项字节和搜索对象结构；它仅作格式对照，不复制或分发微软的 CHM、DLL 或内部表。补丁中的双字节规则由 CP936 字节范围生成。
6. 已取得一次中文全文查询实际命中和列出目标页的界面证据。随后进行改动精简与失败对照，最终补丁仍须重新完成完整矩阵，不能将试验样例的通过直接移作最终验收。
7. Java 侧明确正文、工程输入与导航编码职责，预检不可表示的导航文字，并要求 chmcmd 支持本包的显式编码配置。外部未修改的 chmcmd 会报兼容错误；不再允许它静默生成编码不一致的文档。

修改保存在 `release/patches/chmcmd-encoding.patch`，两个原生构建脚本均应用此补丁。`scripts/check-navigation.cjs` 检查编译后目录/关键字/目标页、文本导航、窗口标题、搜索头与搜索对象；检查结果与 Windows 交互结果分别记录。

跨平台首次回归中，Linux 与 macOS 两种架构已通过；Windows 英文 runner 暴露出校验器命令行中文路径被系统 ANSI 转为问号的问题。后续补丁明确使用 Windows 的 Unicode 参数入口，并仅为本进程设置 UTF-8 的 RTL 文件路径约定。该处理不修改系统语言、注册表或控制台代码页。中文样例增加了中文父目录，以同时检查编译器和校验器的路径处理。
